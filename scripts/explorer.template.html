Multi-party proving · measured & modelled

How fast is co-noir UltraHonk, and where does it stop being practical?

A collaborative SNARK lets several distrusting parties jointly prove a statement over a secret-shared witness — no single party sees the whole witness, yet the output is an ordinary UltraHonk proof. This page tabulates what that costs: every circuit, every prover, ZK and non-ZK, and every network distance between the MPC nodes — from processes on one machine to nodes on opposite sides of the Earth.

Correctness first: the proof is byte-identical to barretenberg.

co-noir's REP3 MPC prover emits a proof that is byte-identical to barretenberg's and accepted by bb's own verifier, for every circuit here, both hashers, ZK and non-ZK — and the single-prover path (plaindriver) is likewise byte-identical to bb. Privacy changes who holds the witness and how long proving takes; it does not change the proof. A skeptic who doubts correctness never reaches the cost question — so this is settled first, in-tree and reproducible.

07 The batch-size dial K

Lookup-heavy pk-gen (the sha256 read-counts) turns each secret table index into a one-hot vector over an MPC round. Doing all gates in one batch is fewest rounds but materialises every vector at once — which hit ~176 GB/party and OOM-killed the box at sha256 2¹⁸. The fix: a batch size K — process the gates in chunks of K. Peak memory ∝ K, communication rounds ∝ gates ÷ K, and the proof stays byte-identical for every K. This is the measured tradeoff on a lookup circuit; drag K to see it.

Peak memory vs. communication rounds, across K
measured ● · memory rises with K, rounds fall with K — the dial picks your point on the curve
peak memory / party pk-gen rounds wall-clock (loopback)
On loopback the wall-clock is nearly flat in K (compute-bound — even slightly faster at small K, from less allocation churn). So K's real tradeoff is peak memory (∝ K) against communication rounds (∝ gates ÷ K) — and rounds only cost wall-clock under network latency. Hence: a smaller K on a memory-tight node or a LAN; a larger K to cut WAN round-trips, until the per-round frame gets too big. The default K=4096 sits near the round-count floor at ~8 GB/party — safe out of the box. Exposed as --lookup-batch-size (proof byte-identical for any value; 0 = unbounded).

08 Model, tiers & provenance

Everything the model assumes, wearing its data on its sleeve. This is a decision-support tool, not a benchmark of record: it never renders a modelled number as measured.

The four deployment tiers

“Same continent” is the larger of a coast-to-coast US hop and a widest-Europe hop (measured cloud inter-region RTTs: US-east↔US-west ≈ 62 ms > widest EU ≈ 35–50 ms), so it takes the US figure. “Antipodal” ≈ London↔Sydney. netem shapes loopback, so RTT = 2 × the injected one-way delay; each tier's delay was ping-verified.

The cost model

  • T(tier) = compute + rounds × RTT + bytes ÷ bandwidth.
  • compute — measured loopback wall-clock per phase (the single-prover baselines are pure compute).
  • latency — sequential rounds × the tier RTT. The band shown spans logical rounds (optimistic, fully-pipelined) → received-messages (conservative, no overlap); reality sits between.
  • bandwidth — received bytes ÷ the tier link rate; ≈0 on the fat local links.
  • Single-prover configs (bb, plaindriver) have zero comms — flat across all tiers.
