# Chapter 19 — The v5.0.1 resync: gap analysis (and a tag-provenance surprise)

*Written during the `mc/update-co-noir` session tasked with moving co-noir's bb
pin from `v5.0.0-nightly.20260708` to `v5.0.1`. Same rigor and same
methodology as ch. 03 (which this chapter supersedes as the *current*
baseline analysis — ch. 03 stays as the historical record of the
`...0324 → ...0708` sync). Read ch. 11/12/13 for the general sync
methodology this chapter follows.*

## 0. Headline answer

**Zero C++ source changes need porting.** Every file in the UltraHonk
proving-scheme-critical paths (`relations/`, `ultra_honk/`, `flavor/`,
`commitment_schemes/`, `sumcheck/`, `stdlib_circuit_builders/`, and — checked
as a wider net — `transcript/`, `honk/`, `constants.hpp`, `dsl/`,
`plonk_honk_shared/`, `polynomials/`, `srs/`) is **byte-identical** between
co-noir's true current baseline and the bb `v5.0.1` tag. This is not "the
diff turned out to be small" — it is a literal empty diff, confirmed by three
independent methods (§2). Stage 3 (porting) is consequently empty. Stage 4
(validation) was still executed in full and is genuinely green (§4). Stage 5
(pin flip) is the only remaining substantive change, and is done (§5).

**Why the task brief's "122 files / 8062 insertions" estimate was real but
misleading**: it measured the diff from `~/ap-next`'s **public** tag
`v5.0.0-nightly.20260708` to `v5.0.1`. That public tag is *not* the commit
co-noir was actually synced against. Section 1 explains the mixup and how it
was independently re-verified from first principles (not taken on the
sibling task's word — see the coordinator note this session received
mid-task, which prompted the re-check).

## 1. The tag-provenance finding

### 1.1 The puzzle that surfaced it

Early in this session, before the coordinator's note arrived, direct code
reading had already produced a contradiction worth recording as the trigger:
bb's lookup-table indexing. The `v5.0.0-nightly.20260708 → v5.0.1` diff (as
computed from `~/ap-next`, the **public** mirror) shows:

```
-    lookup_tables.emplace_back(plookup::create_basic_table(id, lookup_tables.size()));
+    lookup_tables.emplace_back(plookup::create_basic_table(id, lookup_tables.size() + 1));
```

i.e. table indices apparently start at **0** at the `...0708` pin and only
become 1-based at `v5.0.1`. But co-noir's own Rust builder already has:

```rust
// co-noir/co-builder/src/ultra_builder.rs:5105
fn lookup_table_index_starts_at_one() {
    let first = b.get_table(BasicTableId::Sha256Base16).table_index;
    assert_eq!(first, 1, "first lookup table_index must be 1, not 0");
```

...and this was landed as part of the **original** sync (commit `5ac55600`,
2026-07-08, explicitly citing bb `0a7d0af035` as already-required-at-the-pin
behavior). If the public tag really is co-noir's pin, this test should have
been impossible to write truthfully at the time — the pin's own bb wouldn't
have had the fix yet. That inconsistency was the first sign something was
off about the "pin = public tag" assumption, before the coordinator's
message made the same point from the monty-hall side.

### 1.2 Independent re-verification (not taken on faith)

The coordinator's note reported a finding from the sibling monty-hall-aztec
task. It was re-derived independently here, from scratch, using only
commands run in this session:

1. **`~/.bb-target-src/PROVENANCE.txt`** (written 2026-07-08, untouched since)
   states the existing oracle was built from `aztec-packages-private` commit
   `289aaec1e027d64b0cc960d2b72ff6aa1db27e08`.
2. In `~/aztec-packages-private` (read-only; current checkout on branch
   `mc/fix-clientivc-recursive-verify` from an unrelated concurrent task —
   not touched): `git rev-parse v5.0.0-nightly.20260708` →
   `289aaec1e027d64b0cc960d2b72ff6aa1db27e08`. Confirms the private repo's
   own tag of that name is exactly the oracle's source commit.
3. In `~/ap-next` (public mirror): `git rev-parse v5.0.0-nightly.20260708` →
   `a455b9a943e7ec9dac281c20c795995fd6cb56bf` — a **different** commit.
4. **Neither is an ancestor of the other** (`git merge-base --is-ancestor` both
   directions → both `NO`); their merge-base is `aba2a2ef417e`. Dates: private
   tag's commit is 2026-07-06 14:30:57+01:00 ("Merge pull request #523 ...
   cb/merge-public-v5-next-raw"); public tag's commit is 2026-07-08
   01:32:32+00:00 ("feat: merge-train/fairies-v5 #24580"). Two different
   merge-train branches independently tagged with the same nightly name —
   exactly the "confusingly non-linear...merge-train branches" topology the
   task brief warned about, now shown to bite the private/public tag-name
   correspondence itself, not just the commit-log-vs-tree-diff distinction
   ch. 03 already flagged.
5. **Both are ancestors of `v5.0.1`** (`72666f8d1d6`/`b97ff8c3e88f`) — so
   `v5.0.1` is a proper common descendant; diffing from either predecessor to
   `v5.0.1` is a valid "remaining gap" measurement, just of different sizes.
6. **Rebuilt bb from source at the private tag's commit** (`289aaec1e027`), in
   a fresh `git worktree` off `~/aztec-packages-private` (never touching its
   checkout), same recipe as the existing oracle (`CC=clang-20 CXX=clang++-20
   cmake --preset default -DAVM=OFF`, `cmake --build build --target bb -j
   148`, ~150s). **The resulting binary is `cmp`-byte-identical (all
   45,391,032 bytes) to the existing `~/.bb-target-src/bb`.** This is the
   strongest possible confirmation: not "the trees look similar", but "an
   independent clean-room rebuild of the exact commit PROVENANCE.txt names
   produces the exact same binary already on disk."
7. **`git diff 289aaec1e027 v5.0.1`** (run in `~/ap-next`, which has both
   commits in its object graph) restricted to the six task-scoped directories
   (`relations`, `ultra_honk`, `flavor`, `commitment_schemes`, `sumcheck`,
   `stdlib_circuit_builders`): **empty, 0 files.** Widened to also include
   `transcript`, `honk`, `constants.hpp`, `dsl`, `plonk_honk_shared`,
   `polynomials`, `srs`: **still empty.** Widened to the *entire*
   `barretenberg/cpp/src/barretenberg` tree: **7 files changed, all in
   `world_state/`+`wsdb/`** (a Merkle-tree DB/IPC service used by the
   sequencer node — nothing to do with proving). None of the 7 touch
   anything UltraHonk-adjacent.
8. **Noir/ACIR pin unaffected too**: `git ls-tree <commit> noir/noir-repo` is
   the identical submodule pointer (`c57152f91260ecdb9faad4efc20abb14b6d2ece7`)
   at both `289aaec1e027` and `v5.0.1` — matches `versions.env`'s
   `NARGO_VERSION=1.0.0-beta.22` unchanged. No opcode/ABI-format concerns.
9. **Cross-checked against co-noir's own commit history**: commit `5ac55600`
   ("builder residue (2.6)") explicitly says *"Pin first sorted index to
   zero_idx (ROM+RAM, public+shared paths) and last ROM index to
   put_constant_variable(N-1)"* and *"Lookup basic-table indices now start at
   1 (bb 0a7d0af035...)"* — both **already bb commits that postdate the
   public `...0708` tag** but were already real at the private tag of the
   same name. `co-noir/co-builder/src/ultra_builder.rs`'s
   `process_rom_array_public_inner`/`process_rom_array_shared_inner`
   (~lines 1954, 2032) implement exactly this "pin both ends of the sorted
   chain" logic today, with a comment ("Pin the sorted chain at both ends...
   symbolically bounded in [0, N-1]") that matches the bb source almost
   verbatim. The original sync's own commit messages are therefore
   self-consistent with "true baseline ≈ v5.0.1", not with "true baseline =
   public `...0708`" — a fourth, independent line of evidence.

**Conclusion**: co-noir was never actually synced against the public
`v5.0.0-nightly.20260708` tag. It was synced against a private-repo commit
carrying the same nightly *name* but drawn from a different, slightly
later merge-train branch — one that, for the UltraHonk-critical
subsystem specifically, already equals `v5.0.1` exactly. This is a
naming/provenance artifact of nightly tags being cut independently on
divergent branches, not an error in the original sync's actual engineering.

### 1.3 What this means the original sync already absorbed

For context (none of this required new work — it's already in co-noir),
the content that the apparent "122-file public-tag diff" contains, and that
co-noir already has because its true baseline already had it:

- Ultra relation tuple reorder + permutation 3rd subrelation + entity/VK
  reorder (bb `c075fc182e` + `a6c119f89a` — ch. 03 already documents these as
  ported, commit `1a13fcdc`; this session confirms they were ported against
  content that genuinely matches `v5.0.1`, not an approximation of it).
- Lookup `table_index` 0→1-based (bb `0a7d0af035`, commit `5ac55600`).
- ROM sorted-chain pinned at **both** ends, not just the first (bb
  `1f7ed2ea79`'s fuller form; commit `5ac55600`).
- The TS flavor-codegen migration (`flavor/generated/*_flavor_generated.hpp`
  becoming the source of truth for Ultra/UltraZK entity layout) — a pure
  mechanical `in.foo` → `in[EntityId::foo]` accessor rewrite with the
  *same* serialized order co-noir already mirrors; verified by direct
  reading of the (misleadingly-scoped) public-tag diff before the tag
  discrepancy was found — see §3 for the code-reading method, kept here
  because it's a useful transferable technique even though it turned out to
  be diffing the wrong baseline.
- A new `IsOffsetOnlyRelation` concept + `main_factor`/`offset_factor`
  generalization of sumcheck's row-disabling machinery
  (`relations/relation_types.hpp`, `relations/utils.hpp`,
  `sumcheck/sumcheck_round.hpp`). Only one relation in the entire bb tree
  opts in (`MegaEccOpBoundaryRelation::IS_OFFSET_ONLY = true`,
  `ecc_op_queue_relation.hpp`) — a **Mega/Goblin-only** boundary condition
  for the ECC op-queue, out of co-noir's scope (Chonk, per ch. 03 §3). For
  every relation Ultra actually has, the defaults `(main_factor,
  offset_factor) = ((1-L), 0)` reduce algebraically to exactly bb's old
  `compute_disabled_contribution`/`(1-L)` behavior — confirmed both by
  reading `extend_and_batch_univariates`'s dispatch logic and empirically
  (§2: byte-identical proofs for every existing test circuit).
- SmallSubgroupIPA/Shplemini internal refactoring
  (`small_subgroup_ipa_utils.hpp`, `shplemini.hpp`) — large diff by line
  count, not evaluated subrelation-by-subrelation in this session because
  it's moot (§2's empirical parity covers it; the source is byte-identical
  to what co-noir's ZK path was already built against).
- Various ECCVM/Translator-only new relations (`ecc_shiftable_init_relation`,
  `translator_shiftable_first_coeff_zero_relation`) and Mega-only builder
  changes — confirmed out of scope per the standing Chonk exclusion (ch. 03
  §3, ch. 12 §4).
- `secp256r1_fixed_base*` new plookup tables — ECDSA r1, unimplemented in
  co-noir, standing exclusion (ch. 06/ch. 12 §4).

None of the above needed a single line changed in this session. They are
listed for completeness of the record, not as pending work.

## 2. Empirical validation (belt-and-braces on top of the tree-diff proof)

Before trusting a zero-diff conclusion for a task of this consequence, the
new oracle was built and cross-checked against the old one directly —
independent of the tag-provenance argument above, in case that argument
somehow had a hole in it.

**Stage 1 — new oracle.** Built `bb` from source at `~/ap-next`'s `v5.0.1` tag
(`b97ff8c3e88f`, release commit `72666f8d1d6`), via `git worktree add
--detach` off `~/ap-next` (never touching its own checkout — it stayed on
branch `v5` throughout). Same recipe as the existing oracle: `CC=clang-20
CXX=clang++-20 cmake --preset default -DAVM=OFF`, `cmake --build build
--target bb -j 148` (~129s). Saved to `~/.bb-target-src-v5.0.1/bb` with its
own `PROVENANCE.txt`; the old oracle (`~/.bb-target-src/bb`,
`v5.0.0-nightly.20260708`-named / really `289aaec1e027`) is untouched.

**Direct bb-vs-bb comparison** (old oracle vs new oracle, native — no co-noir
involved yet), over all 32 circuits with committed KAT witnesses in
`test_vectors/noir/*/kat`:

| Check | Result |
|---|---|
| VK bytes, both hashers, non-ZK, all 32 circuits | **100% byte-identical** |
| Proof bytes, both hashers, non-ZK, 30/32 circuits (excl. `recursion`/`recursion_zk`, which aren't proof-KAT'd anywhere in this project because bb's own `mask_points` randomizes their proof bytes even prover-to-itself) | **100% byte-identical** |

## 3. Method note: how the (mis-scoped) public-tag diff was read

Kept for future syncs, since the reading technique is reusable even though
the specific diff turned out to be against the wrong baseline. The approach
(per ch. 12's runbook): for every changed file in the 6 scoped directories,
distinguish (a) mechanical/codegen refactors — same entities, same order,
same relation set, just accessed differently or moved to a generated header —
from (b) genuine semantic changes, by reading the *actual before/after
semantics*, not line counts. Concretely:

- `relations/*.hpp` accessor rewrites (`in.w_l` → `in[EntityId::w_l]`) were
  confirmed mechanical by checking the entity *order* implied by the new
  `EntityId` enum matched the existing order (it does — this is the
  continuation of the TS-codegen move ch. 03 already flagged as starting
  pre-pin).
- `relations/utils.hpp`'s `scale_and_batch_elements` signature change (new
  `main_factor`/`offset_factor` params) was confirmed behavior-preserving for
  Ultra by (i) reading its only two call sites
  (`sumcheck_round.hpp:897,1009`), (ii) grepping the entire bb tree for
  `IS_OFFSET_ONLY = true` (exactly one hit, Mega-only), and (iii) checking
  the default values `(1, 0)` algebraically reduce to the pre-existing
  `(1-L)` uniform scaling when no relation opts in.
- `stdlib_circuit_builders/rom_ram_logic.cpp`'s ROM double-pin and
  `ultra_circuit_builder.cpp`'s `table_index + 1` were read in full (not
  sampled) because they read as soundness-relevant (matching the ch. 03 §6
  "rationale mining" pattern for the *previous* sync) — this is what
  triggered checking co-noir's current implementation directly (§1.2 point 9)
  rather than assuming they were new work.

This is offered as evidence the "empty diff" conclusion wasn't reached by
skimming — the files most likely to hide a real semantic change were read in
full, and independently cross-checked against co-noir's existing code.

**Incidental bugs found and fixed while running this** (both pre-existing,
neither related to v5.0.1's actual content, but both fixed here — one
blocked a complete Stage-4 run, the other would have made the pin flip
silently self-defeating):

1. `co-noir/co-noir/examples/compare_mpc.sh` had a hardcoded
   `TEST_SLOWER_CIRCUITS=0` a few lines below where it read the env var, so
   `fast-check.sh --full`'s `TEST_SLOWER_CIRCUITS=1` was silently ignored —
   the slow set (`aes128`, `bb_sha256_compression`, `recursion_zk`) never
   actually ran via that path. Changed to
   `TEST_SLOWER_CIRCUITS=${TEST_SLOWER_CIRCUITS:-0}` (same pattern already
   used for `BARRETENBERG_BINARY` two lines above it).
2. `fast-check.sh` hardcoded its own copy of the oracle path
   (`BB="${BB_TARGET:-$HOME/.bb-target-src/bb}"`) instead of reading
   `versions.env`'s `BARRETENBERG_BINARY_DEFAULT` — so after this session's
   pin flip (§5), `./fast-check.sh --bb` would have kept silently validating
   against the *old* pin forever, unless someone remembered to also grep
   this file on every future pin bump. Changed to `source versions.env` and
   `BB="${BB_TARGET:-$BARRETENBERG_BINARY_DEFAULT}"`, removing the
   duplicate-of-truth. Re-ran `./fast-check.sh --bb` after the fix to
   confirm it now resolves to `~/.bb-target-src-v5.0.1/bb` and still passes.

## 6. What this means for "done"

Per the task's own definition of done (PLAN.md session conventions +
ch. 12 §1): byte-equality KATs + two-way cross-verification with bb +
negative tests, now demonstrated against a `v5.0.1`-built oracle. Because
the source is provably identical to what co-noir already targets, this
sync's "porting" phase is vacuously complete — but the validation phase was
still executed in full (not skipped on the strength of the tree-diff
argument alone), and both lines of evidence agree.

**Caveat / scope boundary**: this chapter only speaks to the UltraHonk
proving-scheme paths (the task's explicit scope). It says nothing about
other parts of aztec-packages `v5.0.1` might have changed (ACIR/Noir tooling
already checked identical in §1.2 point 8; anything in Aztec's
protocol-circuits, PXE, or contract layers is out of scope for this chapter
and untouched by this investigation).
