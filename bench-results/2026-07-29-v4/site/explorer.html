Multi-party proving · measured & modelled

How fast is co-noir UltraHonk, and where does it stop being practical?

A collaborative SNARK lets several distrusting parties jointly prove a statement over a secret-shared witness — no single party sees the whole witness, yet the output is an ordinary UltraHonk proof. This page tabulates what that costs: every circuit, every prover, ZK and non-ZK, and every network distance between the MPC nodes — from processes on one machine to nodes on opposite sides of the Earth.

Correctness first: the proof is byte-identical to barretenberg.

co-noir's REP3 MPC prover emits a proof that is byte-identical to barretenberg's and accepted by bb's own verifier, for every circuit here, both hashers, ZK and non-ZK — and the single-prover path (plaindriver) is likewise byte-identical to bb. Privacy changes who holds the witness and how long proving takes; it does not change the proof. A skeptic who doubts correctness never reaches the cost question — so this is settled first, in-tree and reproducible.

· What counts as “proving time”

Some of the work is the same for every user and every proof of a given circuit, so it need only be done once: parsing the circuit, building its gate structure, the selector / permutation / lookup-table polynomials, committing to those (that is the verification key), and loading the CRS. Everything else has to happen again for every proof, because it depends on the witness. This switch decides which of the two the charts below add up.

What today's binary actually reuses. Of that first category, only the verification key is genuinely precomputed and reused here: it is written once by a separate command and passed into every proof. The rest — the structural build, the precomputed polynomials, the CRS load — is rebuilt on every proof, because co-noir has no way to persist a finalized circuit and reload it. (It can persist a proving key, but that one contains the witness polynomials, so it is per-proof by construction.) So “per proof” is a statement about the protocol's intrinsic cost, not about a switch you can flip today — it is what a deployment reaches once that plumbing exists. The gap is small and worth naming: on this box it is ~1–1.5% of the pipeline, of which the largest single item is a structural build the binary performs purely to decide how much CRS to load and then immediately repeats (0.89 s at poseidon 2²⁰, 0.20 s at sha256 2¹⁶).

Per proof · unavoidable

  • witness extension — solving the circuit's witness under MPC (the MPC nodes' first job).
  • witness assembly — MPC work over the shared values inside the builder, lookup read-counts and tags, memory records, filling the wire polynomials.
  • prove — committing to the witness polynomials, grand products, sumcheck, PCS.

Circuit setup · precomputable once

  • structure — ACIR parse plus building and finalizing the gate trace with an empty witness. Witness-independent by construction, which is exactly why it can be precomputed.
  • precomputed polynomials — selectors, the permutation (σ/id) polynomials, lookup tables.
  • the verification key — the commitments to all of the above.
  • CRS load — depends on circuit size only.
“Proving-key generation” is not this second column. UltraHonk has no reusable per-circuit proving key: what the prover calls the proving key holds the precomputed polynomials and the witness polynomials, and building it is dominated by per-proof MPC over the secret witness. Measured on this box: of the MPC prover's “pk-gen” phase, the precomputable slice is ~0.02% on sha256 2¹⁶ (31 ms of 139.8 s — the rest is secret-index lookup read-counts and the builder's sha gadget) and ~10% on poseidon 2²⁰. Earlier versions of this page let you hide the whole phase, which hid almost entirely per-proof cost. The switch above hides only what a deployment can genuinely precompute — which is why turning it off barely moves the MPC bars while visibly shrinking the single-prover baselines, whose totals are 20–30% setup.

· The four provers, in one minute

Every chart below compares the same proof produced four ways. Two are ordinary single-machine provers (the baselines); two are the collaborative-SNARK provers, where several machines jointly prove over a witness that is secret-shared so no single machine ever sees it whole. All four emit the same UltraHonk proof — they differ only in who holds the witness and how long proving takes.

bb — baseline
Barretenberg, Aztec's C++ prover. One machine, sees the whole witness. The reference the co-SNARK proof must match byte-for-byte, and the speed to beat.
plaindriver — baseline
co-noir's own prover running on one machine with no MPC (the witness in the clear). Isolates the Rust-vs-C++ gap from the cost of privacy.
REP3 — collaborative
3 parties, replicated secret sharing. Each secret is split so any 2 of the 3 can reconstruct it; security holds if a majority stays honest. This is the main co-SNARK prover measured here.
Shamir — collaborative
n parties, any threshold t (Shamir secret sharing). More flexible than REP3 on party count; here it runs the poseidon family only (it doesn't yet support the lookup gates sha256 needs).

02 Distance sensitivity

The single-machine numbers above hide the real question for a distributed deployment: how much does proving slow down as the three nodes move apart? Each dashed line is the modelled wall-clock of one REP3 phase as the round-trip time between nodes grows; each dot is measured — we ran the real protocol on one host while the Linux kernel's network emulator (the tc traffic-control tool) injected each preset's real latency and link speed onto the loopback connection, with the round-trip ping-verified. Witness extension is round-bound, so it climbs steeply with distance; the prove step is bandwidth-bound; witness assembly sits between. The phase named pk-gen in the measured anchors is what this page now calls witness assembly plus a few hundred milliseconds of circuit setup — see what counts as proving time; the anchors keep their measured definition rather than being re-cut after the fact.

04 Circuit composition

What each circuit is made of — because MPC cost tracks composition, not just size. Gate counts are UltraHonk trace-block totals from co-noir circuit-info. Note: boolean constraints and additions/multiplications are fused into the single arithmetic gate in Honk's arithmetization, so they appear inside arithmetic rather than as separate columns (the honest thing to say — they aren't counted separately by the tooling).

Rows = finalized gate rows · dyadic = padded 2ⁿ size the prover actually pays for · witness 0-frac = share of the witness that is zero.
Why does recursion have zero lookup tables? A recursive verifier looks complex, but its work is non-native-field arithmetic (the nnf column: emulating the proof system's other field inside this one, for the pairing checks), plus range checks and ROM — not table lookups. Lookups are how circuits do bit-twiddling and byte decomposition (SHA-256's compression function is almost entirely lookups); a verifier does neither. So recursion is huge (700k rows) yet lookup-free, while a one-block sha256 is small yet lookup-dense — and that, not raw size, is what drives MPC cost.

05 Communication between nodes

The two things that make distance hurt: sequential rounds (each one costs a full RTT — this is why witext explodes on WAN) and total bytes (which the link bandwidth meters out). Measured per phase from mpc-net counters at party 0's busiest peer; round-counts and byte-volumes are network-independent, so these hold at any distance. Witness assembly is split out from the prove step via the mid-run comms snapshot. Circuit setup does no communication at all — it is single-party work — so it never appears here.

rounds = logical blocking rounds (the latency multiplier) · msgs = received messages (conservative round proxy) · bytes = received by the busiest peer.

07 The batch-size dial K

Lookup-heavy witness assembly (the sha256 read-counts) turns each secret table index into a one-hot vector over an MPC round. Doing all gates in one batch is fewest rounds but materialises every vector at once — which hit ~176 GB/party and OOM-killed the box at sha256 2¹⁸. The fix: a batch size K — process the gates in chunks of K. Peak memory ∝ K, assembly rounds ∝ gates ÷ K, and the proof stays byte-identical for every K. K only affects witness assembly; the prove step is unchanged by it. Measured on a lookup circuit — drag K to see the tradeoff.

Circuit: . This is the only circuit K was swept on so far — and the only kind that needs it: only lookup-heavy circuits (sha256) build these one-hot vectors, so K matters for them. poseidon and recursion have zero lookup gates, so K has no effect there. Read across the panels: as K falls, memory drops sharply and assembly rounds climb — but total wall-clock is nearly flat on loopback, because round-trips are almost free on one machine. Flip “assembly + prove → prove only” and both the memory and the wall-clock collapse to a small, flat floor: everything K controls lives in witness assembly; the proving step itself is untouched by K. Why? K only chunks the lookup read-count one-hot vectors, which are derived from secret table indices and so must be rebuilt for every proof — per-proof work that no amount of precomputation removes. The prove step then consumes the finished polynomials and runs the ordinary sumcheck + PCS — and since the proof is byte-identical for every K, what it works from is identical too, so it does exactly the same work no matter how the batching went. K is a memory/round dial on witness assembly, nothing more. So K's real tradeoff is peak memory (∝ K) vs. WAN round-trips (∝ gates ÷ K) — not memory vs. time. Pick a small K on a memory-tight node or a LAN; a larger K to cut round-trips on a long link. The default K=4096 sits near the round-count floor at ~8 GB/party — safe out of the box. Exposed as --lookup-batch-size (proof byte-identical for any value; 0 = unbounded).

08 Model, tiers & provenance

Everything the model assumes, wearing its data on its sleeve. This is a decision-support tool, not a benchmark of record: it never renders a modelled number as measured.

The four deployment tiers

“Same continent” is the larger of a coast-to-coast US hop and a widest-Europe hop (measured cloud inter-region RTTs: US-east↔US-west ≈ 62 ms > widest EU ≈ 35–50 ms), so it takes the US figure. “Antipodal” ≈ London↔Sydney. network emulation shapes loopback, so RTT = 2 × the injected one-way delay; each tier's delay was ping-verified.

The cost model

  • T(tier) = compute + rounds × RTT + bytes ÷ bandwidth.
  • compute — measured loopback wall-clock per phase (the single-prover baselines are pure compute).
  • latency — sequential rounds × the tier RTT. The band shown spans logical rounds (optimistic, fully-pipelined) → received-messages (conservative, no overlap); reality sits between.
  • bandwidth — received bytes ÷ the tier link rate; ≈0 on the fat local links.
  • Single-prover configs (bb, plaindriver) have zero comms — flat across all tiers.
